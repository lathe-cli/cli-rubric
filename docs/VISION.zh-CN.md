# CLI Rubric 愿景

> 面向人类与 AI Agent、公开且可复现的 CLI 体验评测。

[English](VISION.md)

## 当前状态

这是 CLI Rubric 的创立愿景。

它定义项目的目的、价值观、边界和证据标准，但还不是正式评分规范。在项目发布并验证版本化 rubric 之前，不存在任何官方分数、徽章、认证、排名或符合性声明。

评分方法必须通过公开评审、实证验证和独立复现赢得公信力。这份文档无法靠自我声明赋予项目公信力。

## 为什么需要 CLI Rubric

今天的命令行界面同时服务两个存在本质差异的群体：

1. 人类会学习、探索、推理、从错误中恢复，并形成使用偏好；
2. AI Agent 会发现能力、构造调用、解释输出、从失败中恢复，并在明确的预算和安全约束下执行动作。

一个 CLI 可以在技术上提供所有必要操作，却仍然难以理解、充满歧义、不安全，或者让人不愿再次使用。“能用”“好用”“喜欢用”是不同的质量层次。

目前大多数 CLI 指南是定性的；大多数自动检查测量的是规范符合性，而非使用体验；
大多数 Agent benchmark 测量的是 Agent 或模型本身的能力，而不是 Agent 所使用的
CLI 界面质量。简单清单、一次性演示和不透明的 LLM 判断无法填补这个空白。

CLI Rubric 希望把 CLI 体验变成一门开放的测量实践：

- 清晰定义被测概念；
- 方法完全公开；
- 使用真实任务；
- 证据可以重放；
- Human 与 Agent 结果分离；
- 明确表达不确定性和局限；
- 每条规则都允许被质疑。

## 愿景

我们希望每个 CLI 维护者都能用证据分别回答两个问题：

> **Human：**人们能否顺利使用这个 CLI，并且愿意再次使用？
>
> **Agent：**AI Agent 能否在无需猜测的前提下，可靠且高效地使用这个 CLI？

我们希望任何一个公开分数，都可以从最终数字一路追溯到 rubric 版本、评测 profile、任务、命令调用、观察结果和原始证据。

我们欢迎 CLI 作者按照公开标准优化自己的 CLI。如果这些优化真正改善了人类和 Agent 的结果，这个 benchmark 就创造了价值。

## 第一价值：程序性公平

CLI Rubric 不承诺绝对、脱离情境的客观性。任何体验度量都不能诚实地作出这种承诺。

我们承诺的是程序性公平：

- 规则公开；
- 对可比较对象执行相同规则；
- 观察事实与价值判断分离；
- 主观指标明确标注为主观；
- 利益冲突公开披露；
- 不确定性必须呈现；
- 例外必须显式且可评审；
- 评分变化必须版本化；
- 历史证据永久保留；
- 任何人都可以复现、质疑或 fork 这套方法。

公平不是项目口号，而是必须能从方法和产物中观察到的属性。

## “CLI 体验”的含义

CLI 体验是在特定使用情境中产生的结果。它不能仅凭源代码、帮助文本或功能清单推断出来。

因此，每次有效评测都必须声明：

- 被评测的 CLI 及其精确构建产物；
- 任务和目标；
- 目标人类用户或 Agent；
- 其已有知识和可用文档；
- 操作系统、Shell、终端、locale 和执行环境；
- 网络、凭证、fixture 和外部服务；
- 时间、token、工具调用和其他资源预算；
- 操作后果和风险级别；
- rubric 与评测协议版本。

缺少这些上下文的数字，不是官方 CLI Rubric 分数。

## 两个分数，永不合并

CLI Rubric 有两条独立的顶层轨道：

```text
CLI Rubric
├── Human Score
└── Agent Score
```

不存在 Human + Agent 合并总分。

两条轨道可以共享证据采集、任务 fixture 和底层规范检查，但不共享顶层权重；一条轨道的高分不能补偿另一条轨道的失败。

项目可以只发布：

- Human Score；
- Agent Score；
- 或同时并列发布两个分数。

缺失的证据必须标记为“未评测”，不能猜测、静默填补或转换为零分。

### Human Score

Human Score 测量特定人群在特定情境下完成特定目标的结果。

它参考成熟的可用性和使用质量研究：有效性、效率、满意度、交互质量和使用情境。最终公开 rubric 必须自包含并采用开放许可；付费标准可以提供研究参考，但不能成为隐藏的规范依赖。

候选维度包括：

- 上手和可发现性；
- 任务完成和结果正确性；
- 时间、努力和不必要交互；
- 命令、选项和概念的可理解性；
- 反馈、进度可见性和输出可读性；
- 错误预防、诊断和恢复；
- 一致性和学习迁移；
- 安全、可逆性和用户控制；
- 声明终端情境内的可访问性；
- 满意度、信心和重复使用偏好。

Human Score 不能只来自静态 lint。经过验证的评测需要合理组合以下证据：

- 确定性的行为检查；
- 代表性任务完成结果；
- 观察到的错误和恢复路径；
- 时间与交互测量；
- 受控比较；
- 参与者反馈；
- 适用时采用经过验证的问卷。

SUS 等问卷或 NASA-TLX 等工作负荷工具可以提供辅助证据，但它们本身不能完整代表 CLI 质量或“喜欢用”。

每个 Human Score 必须披露参与者 profile、样本、招募方法、任务顺序、研究设计、排除项和不确定性。比较不同 CLI 或版本时，应在适用情况下使用随机化或平衡设计，降低学习效应和顺序效应。

### Agent Score

Agent Score 测量特定 AI Agent 系统在声明的执行 profile 下，通过 CLI 实现特定目标的可靠性与效率。

它不测量 Agent 是否具有感情或真的“喜欢”某个工具。最高档的“偏好使用”意味着：在受控比较中，这个界面持续产生更好的任务结果、更低的交互摩擦，或经过验证的行为偏好。

候选维度包括：

- 能力与命令发现；
- 从意图到调用的正确映射；
- schema、参数和认证信息的清晰度；
- 机器可读输出和稳定错误语义；
- 已完成任务的语义正确性；
- 错误动作的发现和修复；
- 确定性与对环境歧义的抵抗能力；
- 工具调用、token、重试和时间等交互效率；
- 上下文经济性和输出相关性；
- 适用时的安全预览、确认、幂等和可逆性；
- 非交互环境下的行为；
- 从部分失败、过期状态和资源约束中恢复。

Agent Score 必须尽可能将界面质量与模型能力分离。官方评测 profile 因此要求：

- 同一比较中固定任务、预算、prompt 和 harness 行为；
- 对随机系统执行多次重复试验；
- 精确披露模型、提供方、版本、Agent 和 harness；
- 做广义声明时使用有代表性的模型组合，而不是单一偏好模型；
- 在适用情况下使用匹配或配对比较；
- 分解后端失败、Agent 失败和界面失败；
- 明确限制结论可推广到哪些测试集之外的场景。

只要正确性可以直接检查，就应优先使用确定性 grader。只有无法被确定性方法可靠
评判的概念，才允许使用 LLM judge；其 prompt、模型、原始判断、校准集、与合格
人类标签的一致性、失败模式和不确定性必须公开。未经验证的 LLM 意见不是
ground truth。

## 分数区间

每条轨道都有独立的 0–100 分。相同数字区间表达共同的产品追求，但 Human 和 Agent 的被测概念始终分离。

- **0–59——不能用。**人类或 Agent 无法可靠完成声明目标。
- **60–69——能用。**人类可以完成核心目标，但存在明显摩擦；Agent 可以完成核心
  目标，但存在明显摩擦或需要监督。
- **70–89——好用。**人类使用有效、易懂且高效；Agent 使用可靠、可发现且高效。
- **90–100——喜欢或偏好使用。**人类表现出强信心、满意度和偏好；Agent 持续
  表现出低摩擦和更优的受控结果。

区间不重叠：60、70 和 90 都属于下一个等级的起点。

这些阈值是项目最初的语义契约，不是科学常数，也不是 ISO 或其他外部权威提供的标准答案。rubric v1 之前，项目必须验证这些阈值是否对应真实结果中的有意义差异。对阈值含义的实质修改必须发布新的评分版本。

公开分数必须同时包含：

- 所属轨道；
- 分数与等级；
- rubric 版本；
- 评测 profile；
- 证据成熟度；
- 适用时的不确定性或离散程度；
- 重要局限。

如果不确定区间跨越等级边界，报告必须呈现这种歧义，不能给出强于证据的结论。禁止展示没有意义的小数精度。

## 分数是投影，不是证据本身

0–100 的数字有利于传播、回归检测和设定质量目标，但它必然损失信息。

每个顶层分数必须能分解为：

- 维度分数；
- 单项测量；
- 适用的 gate 和上限；
- 原始观察；
- 评分转换；
- 权重；
- 不确定性；
- 被排除或不可得的证据。

权重和聚合规则必须公开并版本化。敏感性分析应说明结论是否严重依赖某个有争议的权重。

有些失败不能被平均掉。一个会损坏数据、失败却报告成功、暴露秘密，或无法完成
关键声明任务的 CLI，不能靠无关的精致功能得到高分。版本化 rubric 可以定义公开
的关键 gate 或分数上限，但触发它们的证据必须可见。

## 评测 profile 与可比性

不存在脱离情境的、诚实的通用 CLI 分数。

官方报告使用版本化评测 profile，声明：

- CLI 类别和能力类型；
- 本地、远端或混合操作；
- 只读、变更或破坏性风险；
- 新手、偶尔使用者或专家人群；
- Agent 组合和自治级别；
- 支持的操作系统和 Shell；
- 交互或非交互执行；
- 文档和网络可用性；
- task pack 与数据 fixture；
- 资源预算。

只有 rubric、profile、task pack、环境假设和重要协议兼容时，分数才可以直接比较。报告不得把不可比的 CLI 排在一起，伪装成测量了同一个对象。

跨平台声明必须有跨平台证据。只在一个操作系统上得到的结果，只适用于该系统。

CLI Rubric 将来可以提供比较视图，但不会从全局排行榜开始。测量有效性优先于竞争。

## 证据包

每次官方评测都必须生成可携带的证据包，至少记录以下内容。

### 被测对象

- CLI 名称、版本、来源和产物摘要；
- 安装方式和依赖锁定信息；
- 声明支持的平台和能力；
- 配置和已启用功能；
- 评测方与被测项目的关系。

### 方法

- CLI Rubric 工具及其 commit 或 release；
- rubric、profile、task pack 和 grader 版本；
- 评分规则、权重、gate 和转换；
- 环境镜像或完整环境清单；
- fixture、生成 seed 和准备流程；
- 相对标准协议的偏差。

### 执行

- 命令调用和工作上下文；
- 经过安全处理的 stdin、stdout 和 stderr；
- 退出状态、时间、signal、重试和资源使用；
- 任务执行前后的状态；
- grader 输入和输出；
- 足以重放评测的顺序信息。

### Human 证据

- 参与者和人群定义；
- 研究说明与任务顺序；
- 观察和衍生指标；
- 以符合伦理和隐私的方式记录问卷与回答；
- 排除项和缺失数据；
- 涉及人类研究时的知情同意、隐私和保留声明。

### Agent 证据

- 评测当时可获得的模型和提供方标识；
- Agent 和 harness 版本；
- system prompt 与 task prompt；
- 工具暴露范围与权限；
- 模型参数、预算和停止条件；
- 完整且安全处理后的工具调用轨迹；
- 每次试验的结果与失败分类。

### 结果

- 组件分数和顶层分数；
- 不确定性、离散程度和试验次数；
- 关键发现、分数上限和局限；
- 机器可读的评分轨迹；
- 证据完整性摘要。

秘密、个人信息和不安全 payload 必须被脱敏，或以安全引用代替。脱敏规则及其对可复现性的影响必须声明。CLI Rubric 不得要求隐蔽遥测。

## 证据成熟度

不是每份报告都拥有相同可信度。

报告必须标明结果属于：

- 实验性结果；
- 可由原评测方重复；
- 已被独立评测方复现；
- 已在显著不同的环境或人群中验证。

具体成熟度模型将公开定义。在得到独立复现之前，结果不能被表述为“已独立验证”。

## 如何赢得公信力

CLI Rubric 不能仅靠引用知名标准或公开源代码借来公信力。它必须验证自己的测量是否真正有效。

方法论计划必须解决以下问题。

### 内容效度

Rubric 维度是否覆盖 Human 与 Agent CLI 体验的重要部分？证据包括公开专家评审、维护者和用户反馈、失败分析及明确记录的覆盖缺口。

### 构念效度

测量是否真正反映它声称测量的概念，而不是 flag 数量或帮助文本长度之类的表面代理？

### 效标效度

更高分数是否能预测更好的任务成功率、更低努力、更强恢复能力和外部观察中的更明显偏好？

### 可靠性

重复运行、不同任务样本、不同合格评分者和独立实现，是否能得到足够一致的结论？

### 鲁棒性

在合理改变模型、人群、环境、任务选择和评分权重后，结论是否仍成立？

### 不确定性

CLI、任务难度、人类、模型、harness、grader 和随机抽样分别贡献了多少变化？报告必须区分“固定 benchmark 上的表现”和“对更广泛潜在任务的推广结论”。

### 外部复现

没有参与设计 CLI 或 rubric 的第三方，能否复现证据并得到兼容结论？

在这些验证工作足以支持分数对应的主张之前，rubric 必须保持“实验性”状态。

## 公平看待优化与刷榜

我们明确允许并鼓励 CLI 作者按照公开 rubric 改善自己的产品。

增加结构化输出、修正退出码、改善帮助、让错误可以行动、减少无意义 prompt、增加安全预览或提高任务成功率，不是刷榜，而是项目希望创造的社会价值。

评测方法必须将这种真实改进与“只针对测试代码提分、却不改善底层体验”的行为区分开。可以采用：

- 多样且有代表性的任务；
- 负向和恢复场景；
- 适用时使用生成式或参数化 fixture；
- 必要时按公开声明的流程执行保留验证；
- 跨版本与跨环境检查；
- 敏感性分析；
- 证明改进能够迁移到单一测试项之外的结果。

项目不会设置秘密质量标准或隐藏权重。如果为保护测量完整性而临时保留某些任务实例，其政策、生成方式、访问规则、公开时间表和利益冲突控制必须公开，并且不能阻止第三方独立复现已经发布的结果。

## 独立性与 Lathe 利益冲突

CLI Rubric 由与 Lathe 有关系的人发起，并位于 `lathe-cli` 组织中。这构成明显的潜在利益冲突。项目会公开承认，而不是假装换个名字就能消除它。

以下承诺是项目根基：

- Lathe 不会获得私有 rubric、fixture、权重、prompt 或例外。
- Lathe 必须使用公开产物，并按照与其他可比 CLI 相同的已发布协议接受评测。
- 只有当公开 rubric 定义了任何 CLI 都能满足的通用结果时，Lathe 特有能力才能得分。
- Lathe 的低分必须和高分一样被诚实发布。
- 报告必须披露评测者、赞助方和维护者关系。
- 在具备足够独立治理之后，维护者必须回避其存在直接利益冲突的重大争议裁决。
- 在出现独立评审者和独立复现之前，项目自己生成的 Lathe 报告必须标记为“维护者生成”，而不是“独立评测”。

任何厂商，包括 Lathe，都不能购买分数、压制有效结果，或获得公开协议之外的提前访问权。

## 开放治理

评分标准属于使用者、被测项目、评测者和研究者共同构成的社区。

治理模型必须提供：

- 对重大 rubric 变更的公开提案；
- 每个标准、权重、gate 和阈值的理由与证据；
- 评分变化的公开评审期；
- rubric、profile、schema 和 task pack 的语义化版本；
- 对历史结果使用方法的不可变标识；
- 纠错和申诉流程；
- 利益冲突披露与回避规则；
- 明确的发布与弃用政策；
- 独立实现和替代权重的空间；
- 认可独立复现的流程。

纠错必须保留审计轨迹。历史分数可以用新 rubric 重新计算，但不得静默改写，伪装成新方法一直存在。

证据 schema 应允许第三方计算替代 scorecard。只有完整遵循官方版本化协议的结果，才可以使用对应版本的官方 CLI Rubric 标识。

## 交付形态暂不决定

项目尚未选择实现语言和最终包装方式。

它未来可能成为：

- 独立 CLI；
- 可复用库；
- CI 集成；
- GitHub Action；
- Agent 或编辑器插件；
- 托管报告查看器；
- 一组开放 task pack；
- 或上述形态的组合。

交付形态必须服从测量设计。项目不会用漂亮工具包装一套薄弱方法。

长期产品是开放协议和证据模型；软件是该协议的参考实现。

## 初始范围与非目标

第一个经过验证的版本应聚焦可以在隔离 fixture 中安全执行的、非全屏命令行程序。

初始非目标：

- 评测底层服务或 API 的整体质量；
- 认证安全、法律合规或生产就绪；
- 评分图形界面、IDE 扩展或全屏 TUI；
- 宣布某个 CLI 框架普遍优于其他框架；
- 只测启动性能或实现代码质量；
- 为不可比的 CLI 类别建立通用排名；
- 用 LLM judge 替代人类研究；
- 把静态最佳实践清单当作完整体验证据；
- 为防止优化而隐藏评分逻辑；
- 给予 Lathe 特权路径。

安全、可访问性、性能和可靠性会在其影响声明体验时参与评分，但 CLI Rubric 分数不能代替这些领域的专业审计或认证。

## 通向可信 v1 的路线

### 阶段 0：创立宪章

- 发布本愿景；
- 披露与 Lathe 的关系；
- 确立 Human 和 Agent 分数永久分离；
- 在方法完成验证前禁止官方评分；
- 邀请社区批评被测概念和治理承诺。

### 阶段 1：开放测量设计

- 定义 Human 与 Agent 构念；
- 发布证据 schema 和实验 manifest；
- 定义评测 profile 与可比性规则；
- 创建确定性参考 fixture 与失败分类；
- 提议 rubric 维度、gate、权重和不确定性报告方式；
- 定义隐私与安全执行要求；
- 在观察 benchmark 结果之前公开验证计划。

### 阶段 2：试点与校准

- 评测不同类型 CLI，包括 Lathe 和非 Lathe 工具；
- 加入故意较差和故意改进的参考界面；
- 对 Human 轨道执行受控人类研究；
- 对 Agent 轨道执行多模型、多 Agent 的重复试验；
- 测量评分者一致性和重测信度；
- 检查结论对任务样本、权重、环境和人群的敏感性；
- 验证分数能否预测外部结果；
- 根据证据校准或修改 60/70/90 的等级含义。

所有试点分数均为实验性结果。

### 阶段 3：Rubric v1

- 冻结经过评审的 v1 协议；
- 发布参考 runner 和机器可读 schema；
- 发布版本化 task pack 与 grader；
- 为参考评测发布完整证据包；
- 记录局限和仍未解决的效度威胁；
- 在声称广泛权威之前支持独立复现。

### 阶段 4：生态信任

- 认可兼容的独立实现；
- 支持第三方 task pack，同时不破坏可比性；
- 建立持久的多方治理；
- 维护长期分数历史，不静默重新解释；
- 只在统计和情境有效性允许时增加比较视图；
- 用公开证据持续演进标准。

## 成功是什么

CLI Rubric 成功时：

- 维护者可以复现一个分数背后的每项发现；
- 有争议的标准可以用证据质疑并公开修改；
- 独立评测者可以得到兼容结论；
- 更高分数能预测更好的真实任务结果；
- 一项 CLI 改进同时提升相关组件指标和外部用户或 Agent 结果；
- 使用者可以区分实验性、可重复和已独立复现的结果；
- Lathe 与任何可比对象受到完全相同的对待；
- 项目愿意按照 rubric 改进，因为这些改进真正帮助了使用者；
- 即使社区不同意某个结果，仍然信任产生结果的过程。

最深层的成功指标不是评测了多少 CLI，而是有多少 CLI 体验因此为人类和 Agent 带来了可测量的改善。

## 最终承诺

CLI Rubric 将先发布证据，再谈权威；先建立方法，再做排行榜；每个分数旁边必须同时呈现局限。

Human 体验与 Agent 体验永远分离。

规则保持公开，实现可以检查，批评成为系统的一部分，按照标准进行的真实改进受到欢迎。

公信力将通过一个又一个可复现结果赢得。
